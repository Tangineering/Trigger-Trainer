# Proposed Changes After the 2026-10-20 Pixel 11 Recordings

This document lists the changes proposed for the next round of work. Each item is a proposal only.
Ricky decides which items go ahead; accepted items get a `D-` entry in `docs/DECISIONS.md`.

**Status (2026-10-20):** the proposals have been turned into `WORK_QUEUE.md` items (P-1 → WQ-001,
P-2 → WQ-002, P-3 → WQ-003, P-4 → WQ-004, P-5 → WQ-005/WQ-006, P-6 → WQ-007 and the parking lot).
The queue is the planning document; this file stays as the rationale, and section 3 is the
specification that WQ-004 cites.

## 1. Findings that drive the proposals

The 13 recordings in `tests/recordings/2026-10-20/` come from one phone: a Pixel 11 running Android
Chrome 155. All 13 pass their drill expectations, and every replay reproduces the live run exactly.
Four findings shape the proposals below.

1. **Platform misdetection.** `isIOS` in `index.html` treats any browser that exposes
   `DeviceMotionEvent.requestPermission` as iOS. Chrome 155 exposes it, so every recording carries
   `device.ios: true`. (Q11, D-44)
2. **Gyro axis order.** The `axis-up` and `axis-right` drills fit only the x/y/z order (the mapping the
   code calls `ios`). The spec order does not fit. The trace is correct on the Pixel only because of
   finding 1. (Q1, D-40 correction)
3. **No contact size.** Every touch reports a radius of 0, so the flat-finger check cannot operate on
   this phone. Whether this is specific to the Pixel is unknown. (`CLAUDE.md`, platform facts)
4. **Shots during an alarm.** In the two `press-wobble` recordings, 5 of 5 shots fired within 0.3 s of
   a movement alarm, all graded Jerked (8° to 50°). These are the cases that Q5 asks about.

Three facts about the recordings also matter for the estimator work in section 3. The motion rate is
60 Hz (median interval 16.7 ms, largest gap 70 ms). `accelerationIncludingGravity` is present in every
sample, and its axes are named explicitly, so gravity provides an unambiguous reference. The three
`safe-move` recordings were made with engine 0.6.0 and older settings; they still pass with the
current defaults.

## 2. Proposed changes

### P-1. Default the gyro axis order to x/y/z on every platform

**Change.** In `engine.js`, `axisMode: 'auto'` resolves to the x/y/z order regardless of platform,
and `createEngine` stops reading `opts.ios`. The `spec` and `ios` values and the `flipH` / `flipV`
settings stay as manual overrides. The Settings label for `ios` becomes "x/y/z (Chrome, iOS)";
the stored value does not change, so saved settings keep working.

**Consequences.** `VERSION` must be bumped, because a phone that is correctly detected as Android
today would produce a different trace from the same inputs. All 13 real recordings replay
identically, because they already ran in x/y/z order. The synthetic recordings are generated in spec
order and would fail; `tests/make-synthetic.js` must write `axisMode: 'spec'` into their settings.
`CLAUDE.md` (gyro axis order paragraph) and `OPEN_QUESTIONS.md` Q1 must be reworded.

**Risk.** The iPhone order is still unmeasured. If an iPhone fits the spec order, the default becomes
wrong there, and the mapping must then be keyed on the browser engine instead of a single default.
P-3 makes that failure visible in the replay test rather than in class.

### P-2. Replace the platform check with feature checks

**Change.** `isIOS` currently controls three behaviours in `index.html`. Each moves to a direct check:

| Behaviour | Today | Proposed |
|---|---|---|
| Fullscreen and landscape lock (`start()`) | skipped when `isIOS` | attempt whenever `requestFullscreen` exists; both calls are already in try/catch |
| Start-screen platform note | iPhone text when `isIOS` | iPhone text when `navigator.vibrate` is absent, since the Android text promises vibration |
| Motion permission | checks `requestPermission` directly | unchanged |

`isIOS` itself becomes a user-agent test (`iPhone|iPad|iPod`, plus `MacIntel` with more than one touch
point for iPadOS) and is used only to label recordings and the debug readout.

**Consequences.** The Pixel regains fullscreen and the landscape lock and shows the Android note. No
engine change and no `VERSION` bump. The recorder's `device.ios` field becomes correct for new
recordings; old recordings keep their stored value.

### P-3. Make the replay test fail when the default mapping is wrong for a phone

**Change.** `tests/replay.js` already prints an "axis verdict" per user agent from the `axis-up` and
`axis-right` recordings. The test additionally replays those recordings with `axisMode: 'auto'` and
fails when the verdict does not include the mapping that `auto` selects. It also warns when
`device.ios` disagrees with the user agent.

**Consequences.** When the first iPhone axis recordings arrive, the test either passes (x/y/z fits) or
fails loudly (spec fits), and Q1 is answered either way. No engine change.

### P-4. Offline axis estimator (tests only, no page change)

Section 3 describes this item in full. The deliverable is a Node script, `tests/axis-estimate.js`,
plus a report in this document or `docs/RECORDINGS.md`. No change to `engine.js` or `index.html` is
part of P-4; run-time use is a later decision (section 3.5).

### P-5. Recording housekeeping

1. Rename `tests/recordings/2026-10-20/` to `tests/recordings/pixel-11/`. `docs/RECORDINGS.md` says
   one folder per phone; a per-phone folder keeps future Pixel recordings with these.
2. Record a long `free` drill (2 to 3 minutes, held still at the end) on the Pixel. The replay prints
   the maximum deviation and answers Q10 (gyro drift).
3. Record `axis-up`, `axis-right`, and one `clean-press` on an iPhone and on a second Android phone.
   These three recordings per phone answer Q1, Q11, and the contact-size question in `CLAUDE.md`.
4. Optional: re-record the three `safe-move` drills with engine 0.7.0, so every real recording has a
   live-equals-replay check. The current files still pass their expectations and can stay.

### P-6. Decisions for Ricky, no code proposed

1. **Q5, shots during an alarm.** The `press-wobble` data shows these shots are already graded Jerked.
   Options: count them as shots (today), count them separately in the summary only, or discard them.
   Each option is a one-line change in `summarize` or the shot tally.
2. **Q2, Clean tolerance.** One `clean-press` shot measured 0.70° against the 0.75° limit; the other
   four measured 0.20° to 0.40°. This is one sample from one shooter and does not justify a change,
   but it is the first data point for Q2.

## 3. Options for building and testing axis estimators from the offline data

### 3.1 Problem statement

The phone reports `rotationRate` as three named components, but browsers disagree on which device
axis each component describes. The engine needs the permutation and the sign of each component.
Gravity, read from `accelerationIncludingGravity`, is unambiguous. When the phone rotates with
angular velocity **w** (device frame), the gravity vector **g** in the device frame changes as
d**g**/dt = −**w** × **g**. An estimator searches for the mapping that makes the measured gyro
components satisfy this relation against the measured gravity.

Rotation about the vertical (a left or right swing in landscape) leaves **g** unchanged and gives no
information. The horizontal axes are therefore found by elimination from the other two, and an
estimator needs some tilt motion before it can decide.

### 3.2 Candidate set

The search space is the 6 permutations of (x, y, z) times 8 sign combinations, 48 candidates. The two
orders the code supports today (spec and x/y/z) are 2 of the 6 permutations. The script should search
all 48, so that an unexpected browser is detected rather than forced into the nearest supported
candidate. A candidate outside the supported two is itself a finding.

### 3.3 Estimators to compare

| ID | Method | Strengths | Weaknesses |
|---|---|---|---|
| E-1 | Derivative fit: low-pass **g**, differentiate, score each candidate by the residual of d**g**/dt + **w** × **g** over samples where \|d**g**/dt\| is large | Simple; already prototyped (section 3.4) | Differentiating a noisy signal; hand acceleration pollutes **g**; margin was thin |
| E-2 | Window integration: over windows of about 0.5 s, integrate the candidate's rotation into a quaternion, rotate the window's initial **g**, and compare with the measured **g** at the window end | Integration suppresses noise; reuses the engine's quaternion code | Window choice; long windows accumulate drift |
| E-3 | Correlation matrix: compute the 3×3 correlation between gyro components and the components of **g** × d**g**/dt; the permutation and signs are read off the dominant entries | No enumeration; one pass; gives a natural confidence (ratio of the dominant to the next entry per row) | Needs motion on at least two axes before all rows are resolved |
| E-4 | Sequential vote: run E-1 or E-2 per sample and keep a running score per candidate; declare a winner when the leader's margin exceeds a threshold for a set time | Models what the page would do live; reports time to decision | Threshold tuning; must handle a change of mind |

E-2 and E-3 are the two worth building first. E-4 is the wrapper that turns the best of them into a
live decision rule and is only needed if run-time use (section 3.5) goes ahead.

### 3.4 Prototype result (E-1, 2026-10-20)

An E-1 prototype was run over the 16 candidates the code supports (2 orders × 8 signs) on all 13
recordings. Every recording ranked x/y/z with no flips first, which matches the axis drills. The
residual of the winner ranged from 0.64 to 0.96 of the measured signal, and the gap to the runner-up
ranged from 0.01 (`axis-up`) to 0.19 (`180-break`). The result is consistent but not yet
convincing; a better gravity estimate and sample selection are needed before any margin threshold can
be set.

### 3.5 Test harness and acceptance

`tests/axis-estimate.js` runs every estimator over every recording and prints, per recording and
estimator: the winning candidate, the margin (best score divided by the runner-up), the seconds of
motion consumed before the running decision last changed, and agreement with the axis-drill verdict
for that phone. The synthetic recordings are a negative control: they are generated in spec order and
must rank spec first.

Acceptance criteria for an estimator, proposed:

1. Correct candidate on every real recording of every phone that has an axis-drill verdict.
2. Margin of at least 1.5 on every recording longer than 5 s.
3. Decision stable within 3 s of motion on the `180-*` and `press-wobble` recordings, which begin
   with the phone already in hand.
4. Spec on every synthetic recording.

When a second phone exists, the criteria are re-run with leave-one-phone-out so that no threshold is
tuned to the Pixel alone.

### 3.6 Deployment path, if the offline work succeeds

Each step is a separate Ricky decision:

1. **Advisory only.** The engine computes the estimate and exposes it in `state`; the debug readout
   shows the estimate beside the active mapping. No behaviour changes; no `VERSION` bump.
   Done (WQ-012, D-57, D-70): `state.axisEst` and the debug readout line `axis est`.
2. **Auto with a confidence gate.** `auto` starts from the fixed default (P-1) and switches to the
   estimate once the margin criterion holds. Changes outputs, so `VERSION` is bumped. The 180 check
   and the trace must restart their integration at the switch, or the switch must happen only before
   downrange is set.
3. **Diagnostics for students.** Out of scope; noted here only so that it is not built by accident.

### 3.7 Harness result (E-1 to E-3, 2026-10-20)

`tests/axis-estimate.js` (`npm run axis-estimate`) ran E-1, E-2, and E-3 over all 48 candidates on
the 15 Pixel 11 recordings and the 11 synthetic recordings. Each estimator ran twice, once per
**gravity source**:

- `lp`: `accelerationIncludingGravity`, smoothed by a centred moving average of ±50 ms;
- `fused`: `accelerationIncludingGravity` minus `acceleration`, which is the gravity estimate of the
  phone's own sensor fusion. Both fields are present in every Pixel sample.

The margin of E-1 and E-2 is the runner-up residual divided by the best residual. The margin of E-3
is the definition in section 3.3: per gyro component, the dominant correlation divided by the next
one, minimised over the three components. The decision time is the motion time (samples with
|**w**| > 10 deg/s) at which the running winner last changed. The full output is
`docs/axis-estimate-2026-10-20.txt`; the whole run takes 0.7 s.

The synthetic recordings contain no gravity. The harness therefore simulates the gravity that a
spec-order phone reports in a fixed hand-held pose (landscape, 15° tilted back, muzzle 5° up). The
synthetic recordings thus test the sign conventions of the estimators, not the physics of a real
phone.

Table 1 gives the result per estimator and gravity source against the criteria of section 3.5 and
WQ-004. "Real > 5 s" counts the 14 Pixel recordings longer than 5 s; "disagree" counts real
recordings whose winner contradicts the Pixel axis-drill verdict (x/y/z, no flips).

| Estimator | Gravity | `xyz` first, real > 5 s | Disagree (of 15) | Min margin, real > 5 s | Margin ≥ 1.5 | Decided ≤ 3 s, `180-*` and `press-wobble` |
|---|---|---|---|---|---|---|
| E-1 | `lp` | 12/14 | 2 | 1.04 | not met | 4/4, met |
| E-2 | `lp` | 13/14 | 1 | 1.55 | met | 4/4, met |
| E-3 | `lp` | 8/14 | 6 | 1.01 | not met | 0/4, not met |
| E-1 | `fused` | 14/14 | 0 | 1.03 | not met | 4/4, met |
| E-2 | `fused` | 14/14 | 0 | 11.47 | met | 4/4, met |
| E-3 | `fused` | 9/14 | 5 | 1.02 | not met | 0/4, not met |

Table 1 supports five observations.

1. E-2 with `fused` gravity meets every real-data criterion. It ranks `xyz` first on all 15 Pixel
   recordings, including the 4.5 s `safe-move`. The smallest margin is 11.47 (`axis-up`); on the
   `180-*` and `press-wobble` recordings the margin is 47.20 or more, and the decision is final
   after at most 0.7 s of motion.
2. The gravity source affects the result more than the estimator does. With `fused` gravity, E-1
   also ranks `xyz` first on all 15 recordings. However, its margin stays between 1.03 and 9.85,
   which is the thin-margin behaviour of the section 3.4 prototype.
3. E-2 with `lp` gravity gives one confident wrong answer. On `axis-up` it ranks `-a+b+g` first
   with a margin of 7.22; this candidate differs from `xyz` only in the sign of the vertical axis.
   The most probable cause is hand acceleration in `accelerationIncludingGravity`, which the `fused`
   source removes. A margin threshold alone
   therefore does not protect an `lp`-based estimator.
4. E-3 does not meet the criteria with either gravity source. The vector **g** × d**g**/dt contains
   no component along gravity. In landscape the vertical axis is device x, so the swings that
   dominate the drills are invisible to E-3, and E-3 most often exchanges alpha and beta (`+b+a+g`).
   Its decision becomes final only after 3.9 to 12.4 s of motion on the `180-*` and `press-wobble`
   recordings.
5. The synthetic control confirms the sign conventions, but only one synthetic recording can
   identify a full mapping. On `180-safe`, which rotates about all three axes, all three estimators
   rank `spec` first (margins: E-1 35.09, E-2 > 999, E-3 1.10). The other synthetic drills rotate
   about one or two axes, so the mapping of the unused components is unobservable. On 7 or 8 of them
   `spec` ties for first place with 2 to 8 candidates, and 2 recordings have no motion above
   10 deg/s. E-2 never ranks another candidate above `spec`. E-1 does so on `180-break`, and E-3
   does so on `safe-move`. Both cases are probably effects of differentiating the step changes in the
   synthetic rates; they were not investigated further.

Against the WQ-004 acceptance lines, the result is as follows. On every real recording longer than
5 s, E-2 with `fused` gravity ranks `xyz` first; with `lp` gravity alone, the criterion fails on
`axis-up`. On the synthetic recordings, the criterion "ranks `spec` first" is met only in the weak
form "no candidate ranks above `spec`" (E-2), because 10 of the 11 synthetic recordings cannot
separate the candidates. The margin criterion (≥ 1.5) and the decision-time criterion (≤ 3 s) are
met by E-2 with either gravity source and not met by E-3.

The scope of this result has three limits. All real data comes from one phone, so the
leave-one-phone-out check of section 3.5 is not yet possible. The `lp` filter is centred and thus
non-causal; the `fused` source is causal and is the only one of the two that a live page can use
without a delay. The iPhone has not been measured, and the presence of `acceleration` on the iPhone
is unverified. Run-time use (section 3.6) remains a separate decision.

## 4. Suggested order

1. P-1, P-2, P-3 together (one engine `VERSION` bump, one documentation pass). The real recordings
   confirm P-1; P-3 guards P-1 against the iPhone unknown.
2. P-5 items 1 and 2 (rename, drift recording), which need the Pixel in hand.
3. P-4 (offline estimators), which can proceed on the existing data in parallel with P-5 item 3.
4. P-6 decisions whenever convenient; nothing depends on them.
